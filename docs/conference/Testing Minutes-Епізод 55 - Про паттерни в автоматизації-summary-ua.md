## Про що випуск

Розмова про принципи написання коду та патерни проектування (Gang of Four) у контексті тестової автоматизації: які з них реально працюють у тестових рішеннях, які надлишкові, і де межа між «структуровано» та «переускладнено».

---

## 1. Досвід гостя та вибір мови програмування (00:02 – 00:13)

- Шлях: manual QA (~6 років) → automation → SDET → QA Lead. Комплекс самозванця зник, коли почав писати код і говорити з розробниками їхньою мовою.
- Мови: C# (старт, через Unity та інді-геймдев), Java (~1.5 року, різниці в синтаксисі майже не бачить), TypeScript, зараз Python.
- **Теза:** «кращої» мови немає. Вибір диктує проєкт — бажано писати тією ж мовою, що й бекенд, щоб не плодити зоопарк технологій.
- **Контраргумент Артема (менеджерська оптика):** мова не критична; критичний **саппорт** — кого потім наймати та хто ревʼюватиме. Експертиза в команді часто і є справжньою причиною вибору мови.
- Ринковий аргумент: Python найпопулярніший (≈30% згадок цього року) → «треба бути в майбутньому».

## 2. Загальні принципи (00:16 – 00:26)

- **Принципи ≠ патерни.** Принципи — необовʼязкові орієнтири; патерни — готові рішення конкретних проблем.
- **DRY** (Don't Repeat Yourself) — виносити повторювані шматки в допоміжні функції. Джуни цього не помічають; навичка виробляється через ревʼю старших колег.
- **KISS** (Keep It Simple) — тестове рішення не потребує всіх патернів світу. Часта пастка: вивчив патерн → одразу хочеш його застосувати, навіть коли він не потрібен.
- **YAGNI** (You Aren't Gonna Need It) — не імплементуй те, що не потрібно зараз. Але думати про розширюваність все одно варто.
- **Практичний індикатор переускладнення:** якщо сеньйор на code review не може розібрати, що ви написали — написано складно, треба рефакторити.
- Досвід гостя: чув докір, що будує «занадто складні» тестові рішення. Частково не погодився (одного Page Object мало), частково визнав — не кожен патерн потрібен у конкретному кейсі. Ліки — навчання команди, а не спрощення заради спрощення.

## 3. Простота vs читабельність — позиція менеджера (00:22 – 00:24)

Артем: **не потрібно, щоб було просто — потрібно, щоб було читабельно.** Системи складні за природою; «просто» означає зрозумілі назви й структуру, а не примітивний код.

> Рекомендація всім, включно з менеджерами: вміти читати код. «Інакше до вас прийдуть і будуть вішати лапшу».

## 4. SOLID в автоматизації (00:26 – 00:38)

Гість: на співбесідах про SOLID питають, але **90% кандидатів не заходять далі Page Object**. Сам про SOLID не питає.

| Принцип | Як пояснив | Застосовність в автоматизації |
|---|---|---|
| **Single Responsibility** | Рознесення логіки по класах/методах. Приклад — Page Object. Антиприклад — клас `Helpers`, куди пхають усе підряд | Висока |
| **Open/Closed** | Створений клас не змінюємо, а розширюємо. Приклад: новий базовий клас для тестів на основі старого, щоб не ламати наявні | Середня — в автоматизації часто щось таки змінюється |
| **Liskov Substitution** | Child-клас не повинен ламати метод parent-класу. Метафора: «батько — лікар, я став гравцем у крикет; це не робить батька гравцем у крикет». Ознака порушення — `NotImplementedException` у частині нащадків | Найнижча, найважча для пояснення |
| **Interface Segregation** | По суті SRP для інтерфейсів — дробити великі інтерфейси на малі | Висока (напр. в Abstract Factory) |
| **Dependency Inversion / Injection** | Не створювати обʼєкти всередині класу, а передавати абстракцію. Приклад: Page Object отримує інтерфейс WebDriver, а не конкретний драйвер | Висока — саме це дає можливість мокати й писати юніт-тести |

**Порада слухачам (Артем):** виписуйте незрозумілі терміни та розбирайте їх окремо. AI-відповіді обовʼязково перевіряйте.

## 5. Патерни Gang of Four (00:39 – 00:59)

Три групи: **creational**, **structural**, **behavioral**. Гість використовував усі creational, частину structural, behavioral — майже ні.

### Creational

- **Singleton** — один екземпляр класу (приватний конструктор + статична властивість). Іноді називають антипатерном. Питання «чому не статика?» залежить від імплементації: статика не завжди дозволяє повернути обʼєкт. Гість давно не застосовував.
- **Builder** — *улюблений*. Ланцюжок `with*()` для моделей із багатьма полями та для самих HTTP-реквестів. Робить тести читабельними «без жодного Cucumber».
- **Factory Method** — ізоляція логіки створення. Класика: створення WebDriver за конфігом (Chrome / Firefox) — викликач не знає деталей.
- **Abstract Factory** — часто плутають із Factory Method. Кейс гостя: `IDbManager` з інтерфейсами під `orders`, `customers`, `users`; заміна MS SQL → PostgreSQL не ламає тести, бо вони працюють з абстракцією — додається нова імплементація, а не переписуються тести. Чесне зізнання: **з чотирьох разів «вистрілило» один раз**; у продуктовій розробці цінність вища, ніж в автоматизації.
- **Prototype** — копіювання обʼєкта зі зміною кількох полів (напр. той самий user, інші імʼя/прізвище). Рідкісний, але корисний.

### Structural

- **Page Object** — не з GoF, але обовʼязковий. Великі сторінки варто **декомпозувати** на секції/компоненти. Альтернативний «onion»-підхід (селектори окремо, методи окремо) гість не любить: «правильного підходу немає, є той, що працює у вас».
- **Page Factory** — фактично мертвий, у Playwright / Cypress ніхто не використовує.
- **Facade** — *дуже любить*. Один entry point: `restRequests.orders.getOrderById(...)` — читається як речення. Так само для роботи з БД.
- **Decorator** — найочевидніший приклад: `test.step()` у Playwright — обгортка навколо функції, що змінює тільки репортинг.
- **Composite** — деревовидна структура; той самий випадок розбиття Page Object на частини.

### Behavioral (згадали як «варто почитати»)

- **Iterator** — кастомна колекція з `next()`.
- **Command** — типові команди компонента, які викликаються ззовні й одна з одної.
- **Strategy** — вибір способу логіну (через API чи через UI).
- **State** — коли юзкейси залежать від стану системи (обидва — гість особисто не застосовував).

### Про Page Object окремо (01:00)

Важливо знати **ідею**, а не форму. Методи краще проектувати **високорівнево** (`login()`, а не набір атомарних кліків) — тоді тест описує дії користувача, і його потенційно може прочитати навіть менеджер.

## 6. Чи варто писати «правильно», якщо через рік підеш? (01:02 – 01:11)

Провокативне питання Артема. Відповіді:

- **Залежить від проєкту.** На продукті тести живуть 5–6 років. Початкова інвестиція в автоматизацію завжди дорожча, але окупається на етапі розширення (`extendable`, не `expandable`).
- Антиприклад із практики: SQL-запити збиралися підстановкою в шаблон із файлу — неможливо було ні прочитати, ні задебажити.
- **Репутація:** IT-світ малий. Якщо систематично «говнокодити» й тікати, про вас питатимуть у попередніх роботодавців. Продуктові компанії таких не наймають.
- **Value:** приємно, коли твої тести працюють і приносять користь через роки після твого відходу.
- **Але баланс:** якщо команда рік проектує «solution мрії» і не написала жодного тесту — цінність нуль або менше. Рецепт: базовий solution → тести → поетапний розвиток за роадмапою. Не намагатися зробити ідеально й одразу.

## 7. Рефакторинг та внутрішня якість (01:19 – 01:24)

- **Внутрішня якість** тестового рішення визначає швидкість додавання нового. Не стежите — далі тільки повільніше й болючіше, maintenance стає основною роботою.
- Рефакторити треба **постійно**: дізнався щось нове — переглянув і впровадив.
- Job security через «тільки я тут розберуся» більше не працює: «прийде менеджер із підпискою на Cursor».

## 8. Патерни в еру AI / vibe coding (01:18 – 01:21)

- Знання патернів і структур даних — **наступний крок після Page Object**, і воно не знецінюється AI, а навпаки: **чим більше контексту ви даєте моделі, тим кращий solution вона побудує.**
- Особистий досвід гостя: без контексту AI будує тестові рішення так, що «я можу краще»; з контекстом — сам обирає доречний патерн.

## 9. Навіщо це все — головний аргумент

Крім якості коду, патерни дають **спільний словник**: ви розумієте розробників і сеньйорів на code review, і вони починають ставитися до вас інакше. Застереження: не викрикувати назви патернів рандомно.

## Ключові тези одним списком

1. Принципи — рекомендації, патерни — рішення проблем. Не плутати.
2. Знання одного лише Page Object недостатньо для сеньйорного рівня.
3. Читабельність важливіша за простоту.
4. Не застосовуйте патерн тільки тому, що щойно його вивчили (KISS + YAGNI).
5. Улюблені патерни гостя: **Builder**, **Facade**, **Factory Method**.
6. Abstract Factory — потужний, але окупається рідко (1 раз із 4).
7. Dependency Injection через інтерфейси — база для мокання й юніт-тестів.
8. Інвестиція в структуру окупається на довгих проєктах, але «solution мрії» без тестів — нульова цінність.
9. Постійний рефакторинг = швидкість у майбутньому.
10. Патерни підвищують якість AI-згенерованого коду, бо це контекст для моделі.
